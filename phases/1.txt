# MM Electricals — Phase 1

## Foundation, Architecture & Data Model

You are the lead software architect and senior full-stack engineer responsible for building a production-grade Windows desktop inventory and shop-management application called:

**MM Electricals**

This is a real business application for an electrical retail/wholesale shop.

We will build this application in 5 controlled phases.

This prompt is ONLY for:

**PHASE 1 — FOUNDATION, ARCHITECTURE AND DATA MODEL**

Do not implement the complete business application yet.

---

# 1. CORE PRODUCT REQUIREMENTS

The final application must:

* Run on Windows as a standalone desktop application.
* Be developed from macOS or Linux.
* Work offline.
* Use a local SQLite database.
* Have a premium modern desktop UI.
* Be maintainable and upgradeable for many years.
* Protect business data from crashes, failed updates and accidental data loss.
* Support future migration to PostgreSQL/cloud/multi-PC architecture without requiring a complete rewrite.
* Eventually be packaged as a professional Windows installer.
* The end user must NOT need Python, Node.js, npm, Django or developer tools installed.

The application should eventually provide functionality similar to a lightweight Vyapar-style business application, but specifically optimized for an electrical shop.

# 3. ARCHITECTURAL PRINCIPLES

Follow these rules strictly:

1. React must never directly manipulate the database.
2. Business logic must not live inside React components.
3. Django views should remain thin.
4. Business operations must use service-layer functions/classes.
5. Use serializers for API validation.
6. Use database transactions for multi-step operations.
7. Every schema change must use Django migrations.
8. Never manually modify the SQLite schema.
9. Avoid unnecessary dependencies.
10. Prefer stable, well-supported libraries.
11. Keep modules separated by business domain.
12. Do not duplicate business logic between frontend and backend.
13. Backend must be the authoritative source for calculations.
14. Frontend should primarily display and collect information.
15. Financial and inventory operations must be atomic.
16. Important records must be auditable.
17. Avoid destructive hard deletes for financial/history records.
18. Design APIs so a future cloud backend can replace the local backend.
19. Keep configuration separate from business logic.
20. Never silently discard user data.

# 11. BATCH-AWARE INVENTORY ARCHITECTURE

This is a critical requirement.

The same product can be purchased at different prices at different times.

Therefore inventory must support batches or purchase lots.

Do NOT simply maintain one stock quantity and overwrite pricing.

Create an architecture for inventory batches.

Example:

Product:
Polycab 2.5 sq mm wire

Batch #001:

* Vendor ABC
* Purchase date 10-Aug
* Purchase cost ₹1,450
* Selling price ₹1,900
* Safe selling price ₹1,750
* Maximum discount 8%
* Remaining stock 4

Batch #002:

* Vendor ABC
* Purchase date 24-Aug
* Purchase cost ₹1,580
* Selling price ₹2,050
* Safe selling price ₹1,850
* Maximum discount 8%
* Remaining stock 20

Historical batch information must NEVER be overwritten.

# 12. PURCHASE-PRICE HISTORY

Design the database so every purchase records historical pricing.

For each PurchaseItem eventually support:

* product
* batch
* quantity
* base purchase price
* supplier discount percentage
* supplier discount amount
* effective purchase cost
* MRP
* selling price
* safe selling price
* maximum customer discount
* notes

The software must preserve the exact values used when that batch was purchased.

# 13. PRICING PHILOSOPHY

The owner controls pricing.

The software may calculate and recommend, but must not silently change pricing.

When entering a new batch, the owner should eventually be able to specify:

* purchase price
* supplier discount
* effective cost
* MRP
* selling price
* minimum safe selling price
* maximum discount
* optional bulk price
* optional customer-specific pricing

These values must be stored historically.

---

# 14. PREVIOUS-BATCH AWARENESS

When a new batch is entered for an existing product, the system must eventually be capable of detecting the previous batch.

Example notification:

"Previous batch detected"

Previous:
Cost: ₹1,450
Selling: ₹1,900
Safe price: ₹1,750
Maximum discount: 8%

New:
Cost: ₹1,580

The owner should later be able to:

* Use previous pricing
* Copy previous pricing and edit
* Set completely new pricing

Do NOT implement the complete UI in Phase 1.

But create the database architecture so this is possible.
